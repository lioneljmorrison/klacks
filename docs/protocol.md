# Client wire protocol (v1)

Clients talk to klacks over a WebSocket at `/ws`. This document describes
the frames. The Go definitions are in `internal/protocol`; keep the two in step.

## Connecting

`GET /ws` upgrades to a WebSocket. The client must be authenticated before
the upgrade; a failed authentication is a plain `401` and no socket is opened.

Until real authentication lands, a dev server (`env=dev`) trusts the identity
the client claims, either as headers or, for browsers, which cannot set
WebSocket headers, as query parameters:

| Header            | Query parameter | Value          |
|-------------------|-----------------|----------------|
| `X-Klacks-User`   | `user`          | user UUID      |
| `X-Klacks-Device` | `device`        | device UUID    |

Servers in any other env do not serve `/ws` yet.

The server pings every connection. A client that stops answering pings is
disconnected; it should reconnect and `resume`.

The server may also disconnect a client that cannot keep up (see
[Backpressure](#backpressure)); the client should reconnect and `resume`.

## Delivery semantics

Messages are fanned out live only after they are durable: a `deliver` frame
never carries a `seq` above the room's committed watermark, and the seqs of
a room's deliveries arrive in order, gap-free, exactly once per connection.
What a connection sees depends on how it joined the room:

- **subscribe** is live-only and best-effort: the subscription is anchored at
  the room's committed watermark at subscribe time, so messages committed
  before it are not delivered, and a message that commits while the
  subscription is being set up may be missed. Clients that must not miss
  anything use `resume` instead.
- **resume** never misses anything: it replays every committed message in
  `(last_seen_seq, hi]` — `hi` being the watermark the replay ends at — and
  then continues live from there, without a gap or a duplicate. Live
  fan-out that lands while the replay is running is buffered and merged in
  order; anything the replay already covered is dropped, not re-sent.

A repeated `resume` re-runs the flow from the given `last_seen_seq`. Sending
the same `last_seen_seq` again can therefore repeat messages; the client
sends its actual furthest-seen seq.

`publish` has no confirmation frame in v1: a successful publish reaches its
sender the way it reaches everyone else, as a `deliver` (live, or replayed by
a later `resume`). A failed publish is an `error` frame naming the room and
`message_id`.

`ack` tells the server the client has consumed every seq in the room up to
`seq`; it lets the server prune its in-memory replay buffer. A client that
never acks still gets correct delivery; only server memory use grows.

## Frames

Every frame is one JSON object sent as one WebSocket **text** message:

```json
{"v": 1, "type": "<type>", ...}
```

- `v` is the protocol version. The server only speaks `1` and rejects
  anything else with `unsupported_version`.
- Unknown fields are ignored, so v1 can gain optional fields. An
  incompatible change bumps `v`.
- UUIDs are strings in canonical form, `xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx`.
  The all-zero UUID is never valid.
- `header` and `ciphertext` are opaque to the server, sent as standard
  base64 (with padding).
- `seq` is a message's position in its room: per room, gap-free, from 1.
- A frame may be at most 88,412 bytes. Larger frames close the connection
  (WebSocket status 1009). The limit fits the largest payload only when
  frames are compact: no whitespace padding, and no escaping of characters
  that need none. Some JSON encoders write `/` (common in base64) as `\/`
  by default; turn that off.

### Client to server

**subscribe**: deliver the room's new messages live. Best-effort (see
[Delivery semantics](#delivery-semantics)); there is no confirmation frame in
v1 — delivery itself is the confirmation.

```json
{"v":1, "type":"subscribe", "room_id":"…"}
```

**resume**: deliver every message in the room with `seq > last_seen_seq`,
then continue live. `last_seen_seq` is `0` to start from the beginning.

```json
{"v":1, "type":"resume", "room_id":"…", "last_seen_seq":41}
```

**publish**: post a message to a room.

```json
{"v":1, "type":"publish", "room_id":"…", "message_id":"…", "device_id":"…",
 "header":"…base64…", "ciphertext":"…base64…"}
```

- `message_id` is generated by the client.
- `device_id` is the sending device.
- `header` may be omitted or empty. `ciphertext` is required.
- `header` and `ciphertext` together may be at most 65,536 bytes (before
  base64). Larger payloads are rejected with `payload_too_large`.

**ack**: the client has every message in the room up to `seq`.

```json
{"v":1, "type":"ack", "room_id":"…", "seq":42}
```

### Server to client

**deliver**: one message, exactly as stored. `room_id`, `sender_id`,
`device_id` and `seq` are the inputs clients bind into the AEAD associated
data, so they are always present.

```json
{"v":1, "type":"deliver", "room_id":"…", "seq":42, "message_id":"…",
 "sender_id":"…", "device_id":"…", "header":"…", "ciphertext":"…"}
```

`header` is omitted when empty.

**error**: a request failed. `room_id` and `message_id` name the request
it answers when the server knows them (`message_id` for a publish).

```json
{"v":1, "type":"error", "code":"payload_too_large", "message":"payload too large",
 "room_id":"…", "message_id":"…"}
```

| `code`                | Meaning                                                    |
|-----------------------|------------------------------------------------------------|
| `bad_frame`           | Not valid JSON, or a field is missing or invalid. `message` says which. |
| `unsupported_version` | `v` is not `1`.                                            |
| `unknown_type`        | `type` is not a client-to-server frame type.               |
| `payload_too_large`   | `header` + `ciphertext` exceed 65,536 bytes.               |
| `not_member`          | The user is not a member of the room.                      |
| `forbidden`           | The user's role does not allow the action.                 |
| `room_not_found`      | The room does not exist.                                   |
| `invalid_argument`    | A request argument is invalid.                             |
| `internal`            | Server error. Details are logged, not sent.                |

`code` values are stable; `message` is for people and may change.

## Backpressure

Each connection has a bounded send queue. If the client consumes frames
slower than the server produces them and the queue fills, the server
disconnects it with WebSocket close code **4000** ("slow consumer: reconnect
and resume"). The client should reconnect and `resume` from the last seq it
delivered; frames it never received are replayed, frames it did receive are
not re-sent.

Resume itself can burst more frames than the queue holds when a client is
far behind: a disconnected client resumes again from its new last seen seq
and makes progress each round.
